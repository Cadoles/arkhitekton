# 8. Data model

PostgreSQL holds all state. The object store holds what is large; the database keeps its
key. Migrations are embedded in the binary and applied by the `migrate` role: see
[10 §10.1](10-operations.md#101-schema-migrations).

Most tables carry a creation time (`created_at`, or a name of their own such as `at`,
`recorded_at` or `added_at`) and many an `updated_at`; they are omitted from the column lists
for brevity.

## 8.1 Identity and access

| Table | Key columns | Purpose |
|---|---|---|
| `sessions` | `id`, `subject`, `username`, `email`, `groups`, `expires_at`, `last_used` | Server-side sessions. The cookie carries the id, nothing else; `groups` are the token's at sign-in |
| `accounts` | `subject`, `username`, `email`, `groups`, `first_seen`, `last_seen` | Everyone who signed in, with a role or waiting for one. Never purged |
| `auth_flows` | `state`, `nonce`, `code_verifier`, `redirect_after`, `expires_at` | In-flight OIDC authorization codes. Purged when expired |
| `user_roles` | `subject`, `username`, `role`, `project_id`, `granted_by`, `last_seen` | A person's own role, globally (`project_id` null) or in one project |
| `group_roles` | `group_name`, `role`, `project_id`, `granted_by` | A role given to a group of the identity provider, globally or in one project; `admin` only globally |
| `bootstrap_grants` | `identifier`, `role`, `claimed_at`, `claimed_by` | Roles waiting for their first sign-in, from `BOOTSTRAP_*` |
| `bootstrap_steps` | `step`, `applied_at` | Which one-off start-up steps already ran |
| `audit_log` | `actor`, `action`, `target`, `payload`, `project_id` | Every administrative act; `project_id` when done on a project's route (a plugin's acts are not attached yet) |
| `instance` | `lock_id`, `id` | The instance's own identity, one row. Labels PipelineRuns so that a run left over from another database is never mistaken for one of ours |

## 8.2 Projects

`projects` — one row per repository Arkhitekton manages:

| Group | Columns |
|---|---|
| Identity | `uid`, `slug`, `label`, `repository`, `forge_url`, `tracker_project` |
| Build | `dockerfile`, `build_context`, `multi_stage`, `targets`, `stack` |
| Images | `image_registry`, `registry_secret` |
| Deploy key | `deploy_key_public`, `deploy_key_secret`, `deploy_key_created_at`, `deploy_key_rotate_requested_at`, `deploy_key_active`, `deploy_key_error` |
| Releases | `version_scheme`, `release_kinds`, `version_file` (committed with the tag at launch) |
| Health | `checked_at`, `check_ok`, `check_note` |

| Table | Purpose |
|---|---|
| `project_pipelines` | Which catalogue kinds this project enables |
| `project_plugins` | Per-project plugin state and settings. **Absence means inheritance** |
| `sync_state` | Cursor and last outcome of each source's synchronisation, per project |
| `issue_status_mapping` | How tracker statuses map to buckets: per project, or instance-wide when `project_id` is null |
| `project_secrets_to_delete` | The Secrets of deleted projects, put down in the same transaction, which the worker deletes from the cluster |

`uid` is the project's unique id, generated by the database and never changed: a project's
Secrets are named from it, `arkhitekton-project-<uid>-git` and `-review`, so that a slug renamed or
reused never points at another project's. `deploy_key_secret` is the name of the key's Secret,
recorded when it was set; keys set before projects had an id keep the name drawn from their slug
until their next rotation. `deploy_key_error` is why the worker could not set the key, shown on
the project's screen and cleared once it could.

## 8.3 Versions and issues

| Table | Key columns |
|---|---|
| `versions` | `name`, `normalized_name`, `status`, `due_date`, `origin`, `tool`, `external_id`, `project_id` |
| `issues` | `version_id`, `subject`, `status_name`, `status_bucket`, `priority`, `assignee`, `done_ratio`, `is_closed`, `tool`, `external_id` |

`origin`, `tool` and `external_id` are what make a tracker optional: a version created
locally and one mirrored from Redmine differ by these columns alone.

## 8.4 Releases

| Table | Key columns |
|---|---|
| `releases` | `project_id`, `tag`, `kind`, `state`, `git_ref`, `git_branch`, `git_commit`, `image_version`, `version_id`, `source_release_id`, `notes_md`, `quality_score`, `manual_actions_md`, `created_by`, `launched_by`, `launched_at`, `released_at` |
| `release_images` | `name`, `repository`, `tag`, `digest`, `size_bytes` |
| `release_notes` | `source`, `pull_request`, `external_id`, `added_by` |
| `release_note_dismissals` | `release_id`, `external_id`, `dismissed_by`: the issues removed by hand from a note, which detecting it again leaves out |

A tag is unique within its project, not across the instance. `source_release_id` links a final
release to the release candidate it was promoted from,
which is how a final release inherits results it did not produce itself.

A release in `draft` has not been launched: `launched_by` and `launched_at` are empty, and
`git_commit` is set at launch. Releases created before drafts existed were launched at their
creation, which is what migration 0071 records.

## 8.5 Queue and runs

| Table | Key columns |
|---|---|
| `jobs` | `kind`, `capability`, `plugin_version`, `priority`, `state`, `params`, `release_id`, `project_id`, `pull_request_id`, `environment_id`, `requested_by`, `attempt`, `queue_reason`, `cancel_reason`, `error`, `run_name`, `exclusive_at_start`, `concurrent_at_start` |
| `runs` | `job_id`, `pipeline_name`, `pipelinerun_name`, `namespace`, `status`, `reason`, `results`, `observed`, `declared_tasks`, `interpreted_at`, `interpreted_by` |
| `task_runs` | `run_id`, `name`, `display_name`, `status`, `reason`, `steps`, `pod_name`, `log_object`, `log_sealed` |
| `queue_limits` | `kind`, `max_concurrent` — an administrator's override of the catalogue |
| `score_weights` | `kind`, `weight` — a pipeline's weight in the score, set by an administrator; absent, its nature's |

`runs.observed` distinguishes a run Arkhitekton created from one it merely watches.
`runs.interpreted_at` says the run has been read into results; `reprocess` clears it.
`task_runs.log_sealed` says the log has been fully copied to the object store and will
not change again.

## 8.6 Results

| Table | Purpose |
|---|---|
| `test_results` | One row per tool and run: `fact_group`, `shape` (`cases`, `findings`, `measures`, `attachments`), `producer` (`plugin@version`), `capability`, `tool`, `status`, counts, `duration_ms`, `summary`, `raw_object`, free `attributes` |
| `result_attachments` | Files kept with a result: `name`, `media_type`, `object`, `size_bytes`, the case it illustrates (`case_suite`, `case_name`), `attributes` |
| `test_cases` | Individual cases of a result: `suite`, `name`, `status`, `duration_ms`, failure message and trace |
| `security_audits` | One row per audit: severity counts, deltas against the previous run, `failed_scanners`, `scanner_status`, `policy` |
| `security_findings` | One row per finding: `fingerprint`, `tool`, `rule_id`, `severity`, `cvss`, package and fix columns, `status`, `suppressed` |
| `bench_measures` | `scenario`, `metric`, `value`, `unit`, `lower_better`, `threshold_ok` |
| `bench_baselines` | The measure pinned as reference for a scenario and metric |

`security_audits.failed_scanners` is why a crashed scanner cannot pass for clean code: a
tool that failed is recorded as failed, not as zero findings.

A release's binaries are no table of their own: a `binary` pipeline's run is a `test_results`
row of shape `attachments` in the `fact_group` `build`, and its files are that row's
`result_attachments`. The release's screen lists them, and neither the tests nor the score read
that group.

## 8.7 Events, plans and automation

| Table | Key columns |
|---|---|
| `events` | `type`, `source`, `project_id`, `subject`, `payload`, `occurred_at`, `depth`, `dedup_key`, `dispatch_pending` |
| `reactions` | `name`, `event_type`, `enabled`, `match`, `plan` |
| `schedules` | `name`, `cron`, `timezone`, `ref`, `enabled`, `plan`, `next_fire_at`, `last_fired_at`, `last_outcome` |
| `release_automations` | The plan a project runs for a release, per project, and its `enabled` switch |
| `plan_runs` | `trigger`, `event_key`, `plan`, `context`, `state` |
| `plan_steps` | `stage`, `position`, `kind`, `ref`, `state`, `job_id`, `detail` |
| `plan_artifacts` | What a step produced: `name`, `kind`, `reference` |
| `pull_requests` | A project's pull requests as last read from its forge: `number`, `title`, `author`, `source_branch`, `target_branch`, `head_sha`, `state` (`open`, `closed`, `merged`), `url`, `draft`, `body`, dates; unique per project and number |

`events.depth` bounds cascades — a reaction that triggers an event that triggers a
reaction cannot recurse indefinitely. `dedup_key` makes a probe that sees the same fact
twice produce one event, and a webhook delivered twice too. `dispatch_pending` marks a fact a
webhook brought: the `api` records it and the worker routes it to the reactions, then clears the
mark.

`pull_request_id` sits beside `release_id` on `jobs`, `test_results`, `plan_runs` and
`plan_artifacts`, with the same meaning: a job launched on a pull request, its results, the plan
its fact opened and what that plan produced. A result takes it from its run's job. The pull request
following keeps its cursor in `sync_state` under `<forge>.pull_request_sync`; `requested_at` there
is an early pass a webhook delivery asked for.

A schedule's run is a plan run whose trigger is `schedule:<id>` and whose key is the tick,
`schedule:<id>:<instant>`: the uniqueness of `(trigger, event_key)` is what keeps a tick seen by
two workers, or again after a restart, from opening two runs. `next_fire_at` is null for a
schedule switched off.

## 8.8 Plugin settings

| Table | Key columns |
|---|---|
| `plugin_settings` | `plugin_id`, `enabled`, `config`, `updated_by` — instance scope |
| `project_plugins` | Same, per project. A missing row means inheritance |

Secret fields inside `config` are sealed with `SECRETS_KEY`; the API never returns them.

| Table | Key columns |
|---|---|
| `capability_bindings` | `ref`, `binding` (the JSON of a catalogue entry, never a service account), `updated_by` |
| `plugin_installations` | `reference` and `digest` as requested, the digest resolved by the worker for a repository or a tag; `follows`, `expected_version` (the tag's), `replaces` (the installation an update replaces); `plugin_id`, `version`, `signed_by` (the key's fingerprint), `object` once pulled; `state` (`pending`, `installed`, `failed`, `removed`, `unrecognised`), `error`, `active` |
| `plugin_sources` | per installed plugin: the `repository` it comes from, `pinned`, what the last check found (`latest_version`, `latest_digest`, `checked_at`, `check_error`), `check_requested_at` |
| `accepted_sources` | `plugin_id` an administrator accepted although the instance recognises neither its signature nor its absence, the `reason` found then, `accepted_by` |
| `capability_state` | a single `version`, moved by every binding and installation change: what the api and the worker watch to rebuild their capabilities |

One version of a plugin is active at a time, and a version is installed once (partial unique
indexes). A removed installation stays, for the record. An installation records its migrations'
version table; the one that was active when its plugin was uninstalled is its `leftover` until the
plugin is purged or installed again, one per plugin.

## 8.9 Tables owned by plugins

An installed plugin's tables live in the same database under its own
migration history (`goose_<id>_db_version` by convention), and are absent from the core's
schema. They may refer to the core's tables; the core's never refer to theirs. An installed
plugin's migrations are applied when it is installed; uninstalling it leaves its tables, which an
administrator may purge: the migrations undone, the version table dropped, the plugin's
`sync_state` cursors forgotten (doc 06 §6.12). The plugin documents them.

## 8.10 Object store layout

    raw/<pipelinerun>/<artifact>                uploaded reports, verbatim
    logs/<pipelinerun>/<task>.log               a task's sealed log, its steps concatenated
    logs/<pipelinerun>/<task>/parts/<NNN>-<step>/<NNNNNNNN>.log
                                                chunks while the task runs, removed once sealed
    attachments/<pipelinerun>/<hash>/<name>     archive members kept as attachments
    plugins/<id>/<version>/sha256-<hex>.tar.gz  an installed plugin's layer, as signed

The worker removes, once a day, what nothing refers to any more: an attachment no result
names (left by an earlier reading whose members differ), the layer of a plugin version no
longer installed and not kept to purge its plugin's tables, and the `raw/` and `logs/` objects of a run the database does not know
(after a reset). Runs are never deleted, so their artifacts and logs otherwise stay: they are
what a replay reads. Nothing younger than a day is touched, and the credentials the worker uses
must allow deleting objects.

An attachment's key hashes the member's path inside its archive, which is free and not a safe
segment; the same member of the same run always gets the same key, so a replay overwrites
rather than piling up copies.

Every key segment is validated before use. Tags are user input, and S3 has no notion of
directory to object to `../`: the check is the only barrier, so a tag like
`../../artifacts` is refused rather than allowed to write outside its prefix.
